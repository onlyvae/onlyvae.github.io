## 0x1 什么是动态库注入
动态库注入(Dylib Injection)是一种代码注入方式，其目的是让进程加载一个额外的动态链接库，注入成功后，动态链接库中的代码与目标程序运行在同一进程地址空间中，可以访问目标进程中的内存数据或者Hook目标程序函数修改执行逻辑。


## 0x2 动态库加载机制
### 0x2_1 Mach-O 格式

在iOS系统中，动态库文件格式为Mach-O，类似linux中的ELF，其结构为：

```
┌──────────────────────────────┐
│ MachHeader                   │  Mach-O 文件头
├──────────────────────────────┤
│ Load Commands                │  加载命令
│  ├─ LC_SEGMENT_64            │
│  ├─ LC_LOAD_DYLIB            │
│  ├─ LC_MAIN                  │
│  ├─ LC_SYMTAB                │
│  └─ ...                      │
├──────────────────────────────┤
│ Segment Data                 │  各 Segment 对应的实际数据
│  ├─ __TEXT                   │
│  ├─ __DATA_CONST             │
│  ├─ __DATA                   │
│  └─ __LINKEDIT               │
└──────────────────────────────┘
```
![mach-o]({{ '/assets/images/mach-o.webp' | relative_url }})

其中MachHeader用于标识当前支持的CPU架构、文件类型以及后面的Load Commands数量。

Load Commands是Mach-O的加载说明，它告诉内核和dyld：
  - 哪些文件区域需要映射到内存
  - 映射到什么虚拟地址
  - 哪些动态库需要加载
  - 程序入口在哪里
  - 符号表在哪里
  - 重定位、导出、绑定信息在哪里
  - 代码签名在哪里

以下是一些常见的Load Command：

| Load Command | 作用 |
| --- | --- |
| `LC_SEGMENT_64` | 描述一个 Segment 以及内部 Sections |
| `LC_LOAD_DYLIB` | 声明依赖的动态库 |
| `LC_LOAD_DYLINKER` | 声明动态链接器路径 |
| `LC_MAIN` | 程序入口点 |
| `LC_SYMTAB` | 符号表位置 |
| `LC_DYSYMTAB` | 动态符号表 |
| `LC_CODE_SIGNATURE` | 代码签名位置 |
| `LC_UUID` | Mach-O UUID |
| `LC_ENCRYPTION_INFO_64` | App Store 加密信息 |

Mach-O在被加载时，以Segment为单位把文件内容映射到进程虚拟内存，Segment决定了映射后的虚拟地址和内存大小，以及内存权限。

例如 `__TEXT` Segment中保存了程序机器指令、字符串常量等信息，内存权限为r-x。在Segment内部使用Section区分不同类型的数据，例如：

| Section | 内容 |
| --- | --- |
| `__text` | 机器指令 |
| `__const` | 只读常量 |
| `__cstring` | C 风格字符串 |
| `__objc_methname` | Objective-C 方法名字符串 |
| `__objc_classname` | Objective-C 类名字符串 |
| `__objc_methtype` | Objective-C 方法类型编码 |
| `__stubs` | 外部函数调用桩 |

### 0x2_2 进程启动流程
在iOS中启动一个App会经历以下流程：

1. 启动请求(SpringBoard/launchd)

    * 用户点击应用图标后，SpringBoard(桌面进程)通过向系统发起启动请求。

    * iOS上所有用户进程都由launchd(PID 1)拉起。launchd调用posix_spawn(底层是fork+exec的组合)创建新进程。

2. 内核创建进程(XNU)

   * 内核创建Mach task，分配虚拟地址空间。

   * 读取可执行文件的Mach-O Header，进行代码签名校验和沙盒配置。

   * 映射主程序进内存，加载主程序Mach-O中 `LC_LOAD_DYLINKER` load command中指定的动态链接器，通常是/usr/lib/dyld，随后将程序运行控制权交给dyld入口

3. dyld阶段

   * 加载依赖库：解析主程序Mach-O的 `LC_LOAD_DYLIB` ，递归加载依赖的dylib。

   * Rebase：修正镜像内部的指针(因为ASLR导致基址偏移)。

   * Bind：绑定符号，如调用外部库的函数、全局变量。

   * 执行动态库中初始化代码:
     * +load 方法
     * C++ 静态构造函数
     * __attribute__((constructor)) 标记的函数

4. 进入 main

    dyld 完成后,根据 LC_MAIN 找到入口,调用 main()。

### 0x2_3 dyld API

dyld在完成进程启动后仍然留在用户进程中，并且提供API用于查询动态库，以下是一些和安全相关的函数。

1. dlopen

    在程序启动后将一个动态库加载到当前进程。可以实现在运行时动态加载链接库，绕过一些静态分析。

    ```c
    #include <dlfcn.h>
    void *dlopen(const char *path, int mode);

    void *handle = dlopen("/System/Library/Frameworks/Foundation.framework/Foundation", RTLD_NOW);
    ```

2. dlsym

    根据符号查找函数地址，然后可以直接调用该函数。这个函数可以用来判断越狱相关符号是否存在当前进程中。

    ```c
    void *h = dlopen("/usr/lib/libSystem.B.dylib", RTLD_NOW);

    void *p = dlsym(h, "malloc");

    typedef void *(*malloc_t)(size_t);
    malloc_t my_malloc = (malloc_t)p;
    ```

3. dladdr

    根据地址查找所属动态库及符号。可以用来判断指定函数是否被Hook进入另一个动态库

    ```c
    Dl_info info = {0};
    if (dladdr((void *)malloc, &info)) {
        printf("Image Path    : %s\n", info.dli_fname);
        printf("Image Base    : %p\n", info.dli_fbase);
        printf("Symbol Name   : %s\n", info.dli_sname);
        printf("Symbol Address: %p\n", info.dli_saddr);
    }

    ;Image Path    : /usr/lib/system/libsystem_malloc.dylib
    ;Image Base    : 0x1a1200000
    ;Symbol Name   : malloc
    ;Symbol Address: 0x1a1234560
    ```

4. \_dyld_*系列

    \_dyld_*系列函数可用于枚举当前进程内加载的动态库。

    | API | 作用 |
    | --- | --- |
    | `_dyld_image_count()` | 获取当前已加载动态库数量 |
    | `_dyld_get_image_name()` | 获取指定动态库路径 |
    | `_dyld_get_image_header()` | 获取 Mach-O Header |
    | `_dyld_register_func_for_add_image()` | 注册动态库加载回调 |


## 0x3 动态库注入方式

### 0x3_1 修改 Mach-O

直接向目标应用的Mach-O中插入 `LC_LOAD_DYLIB` load command 来加载自定义的动态库。

使用这种方式需要对应用重新代码签名，否则系统创建进程时进行代码签名检查会失败，基于该实现的工具：

* [insert_dylib](https://github.com/tyilo/insert_dylib)：命令行工具。
* [TrollFools](https://github.com/Lessica/TrollFools)：手机App，集成CoreTrust代码签名漏洞，可以直接在手机App上对应用插入指定动态库。
* [impactor](https://github.com/claration/impactor)：PC端应用侧载工具，安装应用到设备需要Apple ID。

TrollFools使用案列：

首先实现对 `sysctlbyname` 函数的hook，修改机型参数hw.machine为iPhone99,99，编译生成动态库ModelHook.dylib。

<details markdown="1">
<summary>基于Fishhook Hook sysctlbyname函数</summary>

```c
#include <errno.h>
#include <stddef.h>
#include <string.h>
#include <sys/sysctl.h>

#include "fishhook.h"

static int (*original_sysctlbyname)(const char *, void *, size_t *, void *, size_t);
static const char spoofed_model[] = "iPhone99,99";

static int hooked_sysctlbyname(const char *name, void *oldp, size_t *oldlenp,
                              void *newp, size_t newlen) {
    // Forward unrelated queries and any attempted writes unchanged.
    if (name == NULL || strcmp(name, "hw.machine") != 0 || newp != NULL || newlen != 0) {
        if (original_sysctlbyname == NULL) {
            errno = ENOSYS;
            return -1;
        }
        return original_sysctlbyname(name, oldp, oldlenp, newp, newlen);
    }

    if (oldlenp == NULL) {
        errno = EFAULT;
        return -1;
    }
    if (oldp == NULL) {
        *oldlenp = sizeof(spoofed_model); // Includes the terminating NUL.
        return 0;
    }

    size_t capacity = *oldlenp;
    size_t copied = capacity < sizeof(spoofed_model) ? capacity : sizeof(spoofed_model);
    memcpy(oldp, spoofed_model, copied);
    *oldlenp = copied;
    if (capacity < sizeof(spoofed_model)) {
        errno = ENOMEM;
        return -1;
    }
    return 0;
}

#ifndef MODEL_HOOK_UNIT_TEST
__attribute__((constructor))
static void install_model_hook(void) {
    struct rebinding binding = {
        "sysctlbyname", (void *)hooked_sysctlbyname, (void **)&original_sysctlbyname
    };
    rebind_symbols(&binding, 1);
}
#endif
```

</details>

### 0x3_2 DYLD_INSERT_LIBRARIES 环境变量
`DYLD_INSERT_LIBRARIES` 环境变量类似于linux的 `LD_PRELOAD`，可以让动态链接器dyld加载指定的动态库，但dyld在运行时需要先向AMFI(Apple Mobile File Integrity)查询当前进程安全策略，只有AMFI返回允许从环境变量中加载动态库时，`DYLD_INSERT_LIBRARIES` 才会生效。

> AMFI(Apple Mobile File Integrity)是iOS系统中负责代码签名验证与授权执行的核心安全组件。决定一个程序是否被系统信任、是否允许执行，以及它能够获得哪些与代码签名相关的权限。

AMFI默认禁止普通应用加载 `DYLD_INSERT_LIBRARIES` 环境变量指定的动态库，因此该方案在正常的iOS设备上无效。但在越狱的iOS设备上，越狱工具会对dyld进行二进制修补，修改AMFI函数返回值，使得任意进程都可以通过`DYLD_INSERT_LIBRARIES` 环境变量来注入动态库，随后越狱工具利用 `DYLD_INSERT_LIBRARIES` 环向所有进程注入systemhook.dylib。

### 0x3_3 TweakLoader 插件加载器

严格来说TweakLoader不是一种动态库注入方式，而是越狱环境提供的代码库注入能力，在越狱工具注入的systemhook.dylib中，使用dlopen函数加载TweakLoader.dylib：

>[Dopamine:main.c#L485-L495](https://github.com/opa334/Dopamine/blob/5b1d2c1c3bf54dd8e3641d29c60cd3a0c13cde88/BaseBin/systemhook/src/main.c#L485-L495)
>```c
>// Load tweaks if desired
>// We can hardcode /var/jb here since if it doesn't exist, loading TweakLoader.dylib is not going to work anyways
>if (should_enable_tweaks()) {
>    const char *tweakLoaderPath = "/var/jb/usr/lib/TweakLoader.dylib";
>    if (access(tweakLoaderPath, F_OK) == 0) {
>        void *tweakLoaderHandle = dlopen(tweakLoaderPath, RTLD_NOW);
>        if (tweakLoaderHandle != NULL) {
>            dlclose(tweakLoaderHandle);
>        }
>    }
>}
>```

然后在TweakLoader.dylib中读取插件目录/var/jb/usr/lib/TweakInject/或/usr/lib/TweakInject/加载Tweak插件，每个Tweak包含两个文件：
* Example.dylib：插件的实际动态库。
* Example.plist：插件的注入过滤规则。

Example.plist文件中指定当前插件生效的进程，例如以下配置说明当前Tweak插件只对桌面进程com.apple.springboard生效：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Filter</key>
    <dict>
        <key>Bundles</key>
        <array>
            <string>com.apple.springboard</string>
        </array>
    </dict>
</dict>
</plist>

```

当匹配到生效的进程时，调用dlopen函数加载Example.dylib到当前进程。

Tweak插件一般使用[theos](https://theos.dev/)框架开发，theos提供了Logos语法来简化Hook函数开发。例如Logos语法中对C函数的Hook语法为 `%hookf` ：

```c
%hookf(int, sysctlbyname, const char *name, void *oldp, size_t *oldlenp, void *newp, size_t newlen)
{
	if (!name || !oldlenp || newp || newlen != 0 || strcmp(name, "hw.machine") != 0) return %orig;
	static const char machine[] = "iPhone99,99";
	if (oldp && *oldlenp < sizeof(machine)) {
		memcpy(oldp, machine, *oldlenp);
		errno = ENOMEM;
		return -1;
	}
	if (oldp) memcpy(oldp, machine, sizeof(machine));
	*oldlenp = sizeof(machine);
	return 0;
}
```

### 0x3_4 Task Port 远程注入(frida)

在iOS系统内核中，用Task来描述进程资源管理和执行环境，Task Port是内核提供用于访问和操作Task对象的通信端口，通过Task Port可以实现对目标进程进行内存读写、创建线程。

在正常的iOS系统中，应用进程只能获取自己的Task Port，禁止获取其他App的Task Port。在开发iOS应用时，应用的Entitlements中存在get-task-allow选项，表示允许其他应用获取自己的Task Port，从而允许Xcode调试器对它进行代码调试。

frida server模式就是利用Task Port向应用注入FridaAgent.dylib，注入流程：
1. 获取目标进程 Task port。[frida-helper-backend.vala#L370](https://github.com/frida/frida-core/blob/f564d19f8621434aca53a1ff98e9c0619924e8ac/src/darwin/frida-helper-backend.vala#L370)

2. 通过内存映射的方式将FridaAgent.dylib映射到目标进程，同时还会注入两段引导代码(Mach线程和pthread线程)。[frida-helper-backend-glue.m#L2232-L2542](https://github.com/frida/frida-core/blob/6ed19feb1d6edf7a47f9427c03b0717d4fc6470d/src/darwin/frida-helper-backend-glue.m#L2232-L2542)

3. 调用 `thread_create_running()` 启动Mach线程，PC指向第一段引导代码。在第一段引导代码内创建pthread线程，pthread执行第二段引导代码。[frida-helper-backend-glue.m#L2499](https://github.com/frida/frida-core/blob/6ed19feb1d6edf7a47f9427c03b0717d4fc6470d/src/darwin/frida-helper-backend-glue.m#L2499)、[frida-helper-backend-glue.m#L5026](https://github.com/frida/frida-core/blob/6ed19feb1d6edf7a47f9427c03b0717d4fc6470d/src/darwin/frida-helper-backend-glue.m#L5026)

4. 在pthread线程内调用FridaAgent.dylib代码入口 `frida_agent_main()` 函数，函数内通过socket与frida server建立通信。[agent.vala#L1337](https://github.com/frida/frida-core/blob/6ed19feb1d6edf7a47f9427c03b0717d4fc6470d/lib/agent/agent.vala#L1337)


## 0x4 检测方法
### 0x4_1 动态库枚举

枚举当前进程加载的动态库，判断是否存在第三方dylib，有多种动态库枚举方法：
1. `task_info(TASK_DYLD_INFO)` 从内核中获取

2. 调用dyld提供的函数获取

    dyld函数有两种方式获取加载的dylib：
    * 使用 `_dyld_image_count` 和 `_dyld_get_image_name` 遍历所有加载的dylib，
    * `_dyld_register_func_for_add_image` 函数添加回调函数获取所有dylib。

3. `mach_vm_region` 扫描进程内存，寻找Mach-O Header，再从Mach-O中解析出加载的dylib。

### 0x4_2 DYLD_INSERT_LIBRARIES 环境变量检测

越狱工具使用DYLD_INSERT_LIBRARIES向进程注入systemhook.dyld，但在systemhook.dyld加载后，会特意将改环境变量移除掉：

> [Dopamine: main.c#L374-L379](https://github.com/opa334/Dopamine/blob/5b1d2c1c3bf54dd8e3641d29c60cd3a0c13cde88/BaseBin/systemhook/src/main.c#L372-L379)

>const char *dyldInsertLibraries = getenv("DYLD_INSERT_LIBRARIES");
>if (dyldInsertLibraries) {
>  if (!strcmp(dyldInsertLibraries, HOOK_DYLIB_PATH)) {
>    unsetenv("DYLD_INSERT_LIBRARIES");
>  }
>}
>```

因此在应用内直接读取环境变量实际上是检测不到的，但是dyld会将环境变量写入到CrashReporter中的message2字段：

> [DyldProcessConfig.cpp#L1537-L1548](https://github.com/apple-oss-distributions/dyld/blob/18d3cb0f6b46707fee6d315cccccf7af8a8dbe57/dyld/DyldProcessConfig.cpp#L1537-L1548)
>```c
>if ( security.allowEnvVarsPath ) {
>    char crashMsg[2048];
>    strlcpy(crashMsg, "dyld config: ", sizeof(crashMsg));
>    for (const char* const* p = process.envp; *p != nullptr; ++p) {
>        this->addEnvVar(process, security, allocator, *p, false, crashMsg);
>    }
>    if ( strlen(crashMsg) > 15 ) {
>        // if there is a crash, have DYLD_ env vars show up in crash log as secondary string
>        // main string is missing symbol/dylib message
>        CRSetCrashLogMessage2(allocator.strdup(crashMsg));
>    }
>}
>```

CrashReporter位于dyld的Mach-O镜像中的__DATA,__crash_info，可以从内存中解析读取。

### 0x4_3 frida 检测

frida有两种模式，一种是frida gadget模式，通过向目标应用Mach-O中插入 LC_LOAD_DYLIB load command来加载FridaGadget.dylib，这种方式可以直接通过动态库枚举检测到。

另一种是frida server模式，通过Task Port远程注入FridaAgent.dylib到目标进程。需要注意的是，FridaAgent.dylib默认不通过dyld加载和解析，而是由frida server中的Mapper负责依赖库加载、Rebase和Bind，所以使用dyld相关函数枚举动态库其实枚举不到FridaAgent.dylib，但可以通过内存扫描Mach-O的方式来找FridaAgent.dylib。

除了常规的动态库枚举检测方案，根据frida server注入的流程，可以从以下几点进行检测：

1. 搜索Frida内存特征

    frida server在注入FridaAgent.dylib时，会在目标进程中额外分配一段内存，用于存放引导代码和FridaAgentContext(引导代码运行依赖的内存数据)，其内存布局存在明显特征，可以通过枚举当前进程的内存区间，寻找完全匹配FridaAgentContext的内存区域。

    >[frida-helper-backend-glue.m#L2297-L2309](https://github.com/frida/frida-core/blob/036ec6aedf89b51f45716232d6603a83a6c731bd/src/darwin/frida-helper-backend-glue.m#L2297-L2309)
    >```c
    >...
    >layout.stack_guard_size = page_size;
    >layout.stack_size = 32 * 1024;
    >layout.code_offset = 0;
    >layout.mach_code_offset = 0;
    >layout.pthread_code_offset = 512;
    >layout.data_offset = page_size;
    >layout.data_size = GUM_ALIGN_SIZE (sizeof (FridaAgentContext), page_size);
    >layout.stack_guard_offset = layout.data_offset + layout.data_size;
    >layout.stack_bottom_offset = layout.stack_guard_offset + layout.stack_guard_size;
    >layout.stack_top_offset = layout.stack_bottom_offset + layout.stack_size;
    >base_payload_size = layout.stack_top_offset;
    >...
    >```

2. 线程函数Hook检测

    FridaAgent.dylib内会对三个线程函数(task_threads、thread_suspend、thread_resume)进行Hook：

    >[thread-suspend-monitor.vala#L26-L39](https://github.com/frida/frida-core/blob/8b42e1d3be451fb3b7e1c62a570a68f91502b876/lib/payload/thread-suspend-monitor.vala#L26-L39)
    >```vala
    >construct {
    >    var interceptor = Gum.Interceptor.obtain ();
    >
    >
    >    var kernel = Gum.Process.find_module_by_name (LIBSYSTEM_KERNEL);
    >    task_threads = (TaskThreadsFunc) kernel.find_export_by_name ("task_threads");
    >    thread_suspend = (ThreadSuspendFunc) kernel.find_export_by_name ("thread_suspend");
    >    thread_resume = (ThreadResumeFunc) kernel.find_export_by_name ("thread_resume");
    >
    >
    >    var replace_options = Gum.ReplaceOptions ();
    >    replace_options.replacement_data = this;
    >    interceptor.replace ((void *) task_threads, (void *) replacement_task_threads, null, replace_options);
    >    interceptor.replace ((void *) thread_suspend, (void *) replacement_thread_suspend, null, replace_options);
    >    interceptor.replace ((void *) thread_resume, (void *) replacement_thread_resume, null, replace_options);
    >}
    >```

    这么做的目的是为了隐藏frida server在应用内远程创建的线程，可以读取这三个函数入口指令是否被修改来判断是否被注入FridaAgent.dylib。要确定一定是Frida做的Hook，需要跟踪跳转指令，最终找到FridaAgent内存区域：

    ![frida_hook]({{ '/assets/images/frida_hook.webp' | relative_url }}){: .jailbreak-screenshot}


3. 代码签名状态检测

    frida server在远程注入FridaAgent.dylib之前，会先放宽目标进程调试权限，对目标进程 `ptrace(PT_ATTACHEXC)` 后再 `ptrace(PT_DETACH)` ：

    >[policyd.c#L75-L91](https://github.com/frida/frida-core/blob/036ec6aedf89b51f45716232d6603a83a6c731bd/src/darwin/policyd.c#L75-L91)
    >```c
    >kern_return_t
    >frida_policyd_do_soften (mach_port_t server, int pid, int * error_code)
    >{
    >  gboolean should_retry;
    >  if (ptrace (PT_ATTACHEXC, pid, NULL, 0) == -1)
    >    goto attach_failed;
    >  do
    >  {
    >    int res = ptrace (PT_DETACH, pid, NULL, 0);
    >    should_retry = res == -1 && errno == EBUSY;
    >    if (should_retry)
    >      g_usleep (G_USEC_PER_SEC / 100);
    >  }
    >  while (should_retry);
    >  ...
    >}
    >```

    对进程调用 `ptrace(PT_ATTACHEXC)` 后，iOS系统内核会清除进程代码签名状态位中的CS_VALID，并设置上CS_DEBUGGED，使得进程的代码内存页可以被修改。

    可以通过调用 `csops` 函数获取代码签名状态，判断是否存在CS_DEBUGGED状态位，以及不存在CS_VALID。

    ![csops]({{ '/assets/images/csops.webp' | relative_url }}){: .jailbreak-screenshot}

4. 查询外部修改信息

    调用task_info(TASK_EXTMOD_INFO)读取当前进程被"外部修改"的统计计数，
      * thread_creation_count：其他进程在本进程内创建线程的次数
      * thread_set_state_count：其他进程修改本进程线程寄存器状态的次数
      * task_for_pid_count：其他进程对本进程调用task_for_pid的次数

    当使用Frida注入、Xcode调试或是性能分析工具时，以上三个字段会发生变化。

5. 监听端口探测

    frida server默认监听端口27042，通过探测端口是否开启来判断是否安装了frida，但不能说明当前进程正在被frida注入。
